Chess Town's first visit paints on more cores (step 2 of 2; Eric, Nov 23: "It sounds like we can use more cores").

**What changed**
- A first visit's loading screen pictures are painted ahead by a pool of workers (`town/paint-pool.ts`, `paint.worker.ts`; the device's cores less one, at most 3, `TOWN_PAINT_WORKERS`). They run the main thread's own paint code (`town/paint-jobs.ts`: FrameCache and the roofs call it too). The main thread puts each worker's pixels on its canvas with the same `putImageData`, and paints what no worker has yet. Everything is still painted before the first frame, and the workers stop before it.
- The art goes to the workers as JSON, sent once: only what painting reads (a character's idle frames and their parts, a roof's geometry). The roofs' geometry moved from `boxes.ts` to `box-geom.ts` (moved, not copied), so the worker is 13 KB.
- No OffscreenCanvas is needed (the pixels come back as buffers). With no workers, a worker that fails, or art that can't go into JSON, the main thread paints as before, silently.
- A grid's row is built with a plain loop (`houses/kit.ts`: the same strings).
- Switches: `?paintworkers=N` (anyone's; 0 = main thread only, as before) and `?paintslow=K` (tests: CDP's CPU slowing doesn't reach workers, so this slows them the same way).

**What players see:** the first visit's loading screen is about half as long. Nothing else changes: every picture is identical.

**Numbers** (same machine, iPhone 13 emulation, CPU 4x, tap to first frame, 3 runs each, main `82bf8db7` vs this branch, workers slowed 4x too):

| | main | this branch |
|---|---|---|
| first visit | 20.8, 21.6, 21.5 s | 11.6, 11.8, 13.2 s |
| second visit (kept pictures) | 6.8, 6.4, 7.1 s | 6.0, 6.7, 7.8 s (unchanged) |
| walking fps (headless, software GL, median of 4) | phone 10.8, computer 12.15 | phone 10.85, computer 12.1 |

Not 4x because the parts' lazy grids (a closure per part) can't go to a worker. They stay on the main thread with putting pixels on canvases and uploading. A real iPhone's other cores are slower (one more performance core, four efficiency cores), so expect less gain there.

**Checks** (lane: targeted, the town's loading; frame rate measured above)
- New `packages/app/test/town-paint-workers.test.ts`: every frame (light and darker) and every roof of an admin's town painted from the worker's JSON copy is byte-identical (a copy missing `halo` failed 998 of 2,430), plus the pool's paths: worker count, waiting and painting meanwhile, a broken worker, a picture that can't be sent, one a worker can't paint.
- `e2e/perf.spec.ts` (`@perf`, run 3 times here, all passed): the town loads are slowed with `?paintslow=4`. First-visit bound `TOWN_LOAD_REFS` changed **20 → 12** reference jobs (measured 8.9 to 11.0, median 9.6). New check: the workers painted more than half the pictures. The kept-pictures test adds a third visit painted on the main thread alone (`?paintall&paintworkers=0`), whose picture hash must equal the first visit's (painted by the workers). It passes. Unchanged: the longest task under 2 refs (1.4 to 1.6), the loading screen under 3 s, the second visit under 6 refs (4.7 to 5.3).
- No checks removed. `e2e/town-street.spec.ts` "the town's loading screen…" passes locally.
