## Resume: a tap starts the game or says why, never the card again

Main's full run on `9e0dce2` (run 45088115360, shard 11) was red on a flake: `[phone] xp.spec.ts:382`. Resume closed the card, no match started, and the card came back (Resume focused, no error line).

**Cause.** A file the resume loads (the solo game's code) failed to load. `stale.ts` reloads the page for a missing chunk (its fallback for a deploy's removed files), and the reloaded page offered the card again: the tap was lost. Every other path either sets home's error line (ended, paused, another tab, couldn't resume) or can't bring the card back on the same page: the card's state is set again only by the load or by Boss Battle opening, and the snapshot rules out both. Staged locally (the solo chunk aborted until the page reloads), main gives the CI failure's screen exactly, down to the snapshot's refs (`alertdialog [ref=e91]`, `Resume [active] [ref=e99]`).

**What changed (`App.tsx` `resumeKept`, `solo-kept.ts`):**
- While a Resume loads, this tab notes its game (`noteResuming`, sessionStorage `brc.resuming`). A page loaded within a minute takes the note once and resumes as the card for that game comes, in a layout effect before the card is drawn. Cleared once the loads settle.
- A load that rejects (the openings' chunk, an engine) says "Couldn't load the game. Check your connection and try again." It used to leave home with the spinner state on and nothing said (an unhandled rejection).
- A second Resume while one is loading is the same Resume (a ref), never two matches racing.

**What players see.** A Resume tap that hits a missing file reloads the page and goes straight into the game, instead of showing "You have a game in progress" again. A Resume whose load fails says so on home. Nothing else changes.

**Lane.** Targeted (a UI race in the Resume flow; no stored data or protocol). Specs: `e2e/xp.spec.ts` (the Resume flow) and `e2e/battle-tower.spec.ts` (same loads, floors), both phone, locally: 23 passed.

**Checks changed (old → new):**
- `xp.spec.ts:382` (the reload's card): the reload's `/api/me` slowed by 1.5 s and Resume tapped as soon as the card shows. Before, the test read the profile over HTTP between the card showing and the tap. That record check (nothing recorded) now runs after Resume, with a check that the card stays gone once it's your turn.
- New, in `xp.spec.ts`: "Resume whose game won't load: the page loads again and the tap goes on there". Service worker blocked (it answers from its copy), the solo chunk aborted until the page reloads. It asserts the abort happened, the second load, your turn on the same board, and no card. On main's app it fails exactly as CI did (`phase` undefined, card back); with this PR it passes (6/6 in a probe, then in the spec run).
- New, in `app/test/stale.test.ts`: the carried tap is taken once, for that game alone, within the minute, never after the resume is in or without storage.
- None removed.

**Known, left as is.** `startSolo` and `startTowerFloor` await the same loads with no catch, so a rejected openings or engine load leaves them silent the same way. Follow-up. Why the chunk failed on the runner isn't in the logs (the server log is quiet at the tap). A dropped dev-proxy connection that survives its one retry is likely; on a phone a flaky network does the same.
