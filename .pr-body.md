## The Boss Battle screen's CI hang: a watchdog that names the code (cause not found)

**This PR is the diagnostic, not a fix.** I couldn't find the cause within the budget, so the next hang will report where the page is stuck.

### What we know now
- **Why a 5 s expect ran for 5 minutes:** Playwright 1.56's `expect` makes its first check with no timeout (`frames.js`, `noAbort: true`), so a page whose main thread never answers holds that first check until the test's 300 s timeout. I confirmed this locally: a 45 s busy loop in the page held `toBeVisible()` (5 s) for 45 s. That's why both hangs (moo.spec Nov 20, boss-bar.spec:301 Nov 24) stopped at the same line and left no trace.
- **Not reproduced:** no hang in any of these runs, all with the watchdog on:
  - 16 runs of both tests' loops at 6× CPU slowdown (`Emulation.setCPUThrottlingRate`);
  - boss-bar.spec ×3 on desktop (the hung test ran 3 times);
  - moo.spec ×2 on phone.

  This machine has headless shell 1243; CI's image has 1194.
- **Ruled out:**
  - every loop on the Boss Battle screen's path is bounded (the stage's prewarm slices, `lazyAnimsTogether`, `selectLine`, `rowSizes`);
  - a dropped match chunk recovers (tested with a route abort);
  - the stage draws with `putImageData`, which doesn't read anything back from the GPU;
  - the kept battle's re-offer on opening the screen (Nov 22) arrived after the first hang (Nov 20).

### What changed
- `e2e/helpers.ts`: `watchRenderer` on every test's `page` (the shared `test` fixture). It opens a CDP session with the Debugger domain alongside the page, because once a page hangs, a new session gets no answer (tested). It pings every 10 s. If a ping gets no answer for 30 s, it calls `Debugger.pause`, which gets through to a busy main thread even though an evaluate doesn't. It then reads the stack with about 160 characters of code on each side of each place, resumes, prints the result to the job log as `[renderer-hang] <test>` and attaches it to the test (the HTML report).
- It also reports:
  - when a hang ends ("answered again N s after"), so a long slow stretch reads differently from an endless one;
  - "didn't pause either" when no script is running: the hang is in layout, painting or decoding, or the browser itself is stuck;
  - "timed out with the page still answering" when the wait was Playwright's, not the page's.
- It never fails a test. The `@perf` specs aren't watched. Teardown waits at most 2 s on detaching the session: a hung page held an unbounded detach for 5 minutes.
- Cost on a passing test: about 25 ms (sum of 14 boss-bar tests over 3 runs each: 23.6 s with it vs 23.3 s without, inside the run-to-run spread).

  - `docs/areas/ops.md` (CI e2e: "A page that stops answering names its code").
