## What the game does to the sound (read in a real browser)

I ran Chromium on the built app with `wrangler dev`, in Jefferson's battle, with `AudioNode.prototype.connect` wrapped before the app loads. Every music source's path, as recorded:

```
AudioBufferSourceNode (intro, 10.67 s, rate 1, detune 0) -> GainNode (0.25 = MUSIC.volume) -> GainNode (0.9 = musicOut) -> AudioDestinationNode
AudioBufferSourceNode (loop, 114.33 s, loop, rate 1)     -> GainNode (0.25)                  -> GainNode (0.9)            -> AudioDestinationNode
```

- **No filter, no compressor, no duck** on music's path since #697. Every music path goes through `startPlan(bus.ctx, bus.out, …)` into `musicBus().out`: the battle, the room, the splash and the rebuild's handover (music.ts:478, 582, 633, 737). There is no second path, so nothing else needed removing.
- **Level:** 0.25 × 0.9 = 0.225 (MUSIC.volume × the master's 0.9), as intended.
- **Sample rate:** the files are 48 kHz. The test browser's context ran at 44.1 kHz, so `decodeAudioData` resamples each file once, as it decodes. That's normal and inaudible, and a 48 kHz device plays them as they are. playbackRate is 1 and detune 0.
- **Stale builds:** pages are fetched fresh (network-first), and the worker updates itself (skipWaiting, then claim). But `/music/` is answered cache-first, so the first open after a deploy can still play the old MP3s, because the old worker answers until the new one takes over and drops the old caches. **To hear a new build, Eric closes the app or tab fully and opens it again, twice.** Fixed alongside: the worker's version left the music out of its hash. It only changed on a music-only deploy because the bundle happens to carry the commit. `vite.config.ts` now hashes `/music/` into the version. Checked: a one-byte change in `public/music/` gives a new `brc-…` version.

## What changed

- **Every theme re-rendered from its song** (never re-encoded): stereo, constant 192 kbps, 48 kHz. That's all 27 MP3s, including the Hidden Boss's four themes. On `claude/trailer-v2`, `handoff.py` and `phases_v.py` gained `--stereo --kbps N` (pushed there, commit 1cd086ea; the default is still mono 64).
- **themes.json:** no length changed. Only the recorded `lufs`/`peakDb` numbers moved, by 0.1 to 0.9 dB, to match what ships.
- **Levels:** within 0.3 dB of before for every file (worst: folio-intro and recluse-phase2-intro, +0.3), measured as heard (a mono file plays on both speakers).
- **Loop seams:** I decoded each loop with ffmpeg and correlated a 50 ms window at loopStart with the one at loopEnd. Every loop's best lag is 0.00 ms (correlation 0.992 to 1.000).
- **Docs:** the music README, docs/areas/bosses.md and town-square.md, and `docs/decisions/2026-11-14-music-full-quality.md`.
- **One focused check** added to Jefferson's music test (e2e/grex.spec.ts): the music's path is `source > gain > gain > speakers`.

The town still waits at most 3 s (`MUSIC.townWaitMs`) and the rest lands behind it, so opening the town is no slower, but on 6 Mbps the background fetch runs for about a minute. Decoded memory (float32, one theme at a time, as before) doubles: a two-minute theme goes from 22 to 44 MB at 44.1 kHz (48 MB at 48 kHz). The largest is Dash's at 57 MB, then the Hidden Boss's phase 2 at 53 MB.
