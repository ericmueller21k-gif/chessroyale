## Town repeat visits: upload the kept atlas pages whole

**Lane:** targeted (town drawing and load path). Briefs: `notes/briefs/town-atlas-pages.md`, round 2 `notes/briefs/town-atlas-pages-2.md`.

### What changed
- The kept pictures' PNG pages are now packed the way the WebGL atlas packs (`paint.ts` `ATLAS`: 2048 px pages, 2 px padding, a picture over 1024 px alone; manifest v2). On a repeat visit, each decoded page goes into one atlas layer in a single upload (`paint-gl.ts` `adopt`, uploaded by `kept`). The 1,912 pictures are no longer cut out and uploaded one at a time.
- Each picture is now a stand-in canvas. It stays empty until something reads its pixels (hit tests, statue masks, through its 2D context; since round 2 also a 2D context drawing from it) or the painter has to upload it alone (after a lost context, or `changed`); then it's cut from its page (`keep-pictures.ts` `domPageIO`). The decoded pages stay in memory until the town closes, about the same memory the cut canvases used to take.
- `TOWN_PICTURES.pagePx` is removed: the page size is the atlas's now.
- Fixed on the way: the painter kept its framebuffer across a lost context, and after a restore it pointed at a dead one (`readFb`).

### Measured (headless Chromium, software WebGL, repeat visit, tap to first frame, 4 runs each, main and branch back to back)
| | main | this branch |
|---|---|---|
| 4x slowed | 5.42–5.59 s (median 5.47) | 4.42–4.81 s (median 4.52) |
| 4x, the load itself | 3.05–3.35 s | 2.32–2.60 s |
| 1x | 2.15–2.40 s | 1.61–2.27 s |
| 1x, the load itself | 0.87–1.09 s | 0.66–0.85 s |

At 4x, cutting is gone (−1.15 s), but whole-page uploads add +0.35 s: about 50–65 ms a page here, because the browser converts each bitmap on the main thread. That's why the saving is ~1 s, not the brief's estimated ~3 s. Ideas measured and not used:
- Decoding in workers: slower. The browser already decodes `createImageBitmap` off the main thread.
- Raw-byte uploads: about 3× quicker in a bench (6 / 19 ms a page), but they need a new storage format. A possible follow-up; see the decision note.

## Round 2: blank boss faces on a repeat visit

CI (run 45605985953, shard 5) failed `e2e/town-controls.spec.ts:347` on phone and desktop: "every portrait drawn" 0 of 21. The chips (`Town.tsx` `drawFace`) and the large map (`TownMap.tsx` `Face`) draw `r.chipFace(…).img` onto their own canvas. Drawing *from* a canvas never calls its `getContext`, so they copied an empty stand-in.

**Fix (one place, for every reader):** the first stand-in that's made wraps `CanvasRenderingContext2D.prototype.drawImage` and `createPattern` (`keep-pictures.ts` `cutBeforeDraw`). A 2D draw from a stand-in that hasn't been cut yet cuts it first. Two other ways were considered:
- Cutting in `chipFace` only: a future 2D reader would bring the bug back.
- Cutting in `FrameCache.get`: the WebGL painter calls it every frame, so every picture would get cut while you walk.

Cost: one WeakMap lookup per 2D `drawImage`, and only after a repeat visit has started (never on a first visit or with a 2D painter).

**Audit: what can get a stand-in and draw from it without its own `getContext`:**
| Consumer | Gets a stand-in? | Now |
|---|---|---|
| Chips (`Town.tsx` `drawFace`), large map (`TownMap.tsx` `Face`), via `chipFace` | **Yes** (the bug) | Cut by `cutBeforeDraw` |
| render.ts's 2D painter path (`ctx.drawImage(img…)`, `blitSoft`'s scratch canvas, light layers) | No: a 2D painter has no `keep`, so no shelf and no restore; a WebGL failure reloads the page, so there's no mid-visit swap | Also covered by `cutBeforeDraw` |
| The same calls on WebGL (`GLCtx`, `soft`, GL layers) | Yes, as the painter's own draws | Read from the adopted atlas page; a picture uploaded alone (lost context, a page `adopt` couldn't take, `changed`) is cut first (`paint-gl.ts` `upload`, `e.stand`) |
| Hit tests, statue masks, `pawnFace`, the sprite strip's `face()`, `__townPictureSum` | Yes | Read through `getContext`: already cut |
| Save (`createImageBitmap(cv)` in the compose worker IO) | No: runs on a first visit only (`pics.from` is null) | n/a |
| rides, you-look, sky, zzz, shops | No: their pictures aren't kept | n/a |

**The gain is kept:** the @perf test "a second visit…" (`e2e/perf.spec.ts`) gave 5.05 s for the second visit against 10.2 s for the first on this container. The fix only cuts what a chip or the map draws, at most a few dozen pictures.

### Player-visible
- Nothing looks different; a repeat visit to the town loads sooner. With round 2, the chips' and the large map's boss faces are drawn on a repeat visit too (they were blank).

### Checks changed (old → new; none removed)
- `__townPictureSum()` (the guard hash in `e2e/perf.spec.ts`, "a second visit…"): it hashed the pictures' canvases; now it also returns `gpu`, a hash of what the atlas holds for each picture. The spec's `toEqual` therefore also compares the GPU side across the three visits (first visit, second with kept pages, third painted without workers). The spec file itself is unchanged.
- `e2e/town-street.spec.ts`, "the town's loading screen…": it checked zero uploads while walking on both visits; it still does, and now also loses the WebGL context on each visit and checks that every picture uploaded again holds the same texels as before.
- `town-keep-pictures.test.ts`: the packing test now checks the atlas layout (pages no bigger than the atlas's, padding clear, big pictures alone). Restore is tested for its pages and its stand-ins. Two new odd-entry cases: a v1 entry and a page bigger than the atlas's.
- Round 2, `e2e/town-controls.spec.ts`, "the minimap…": before its reload it waits for the first visit's pictures to be saved (`pictures.saved > 0`) and after it checks `pictures.kept`, so CI's run is always a repeat visit. New check: every chip shown has its face drawn (pixels not blank). It fails without the fix ("0 of 4") and passes with it.

### Run locally (round 2)

- `e2e/town-controls.spec.ts` (phone and desktop) and `e2e/town-street.spec.ts`: 31 passed, 2 skipped (stills).
- `e2e/perf.spec.ts` "a second visit…" @perf (phone): passed, with the canvas and GPU hashes the same on all three visits.
