## Town repeat visits: upload the kept atlas pages whole

**Lane:** targeted (town drawing and load path). Brief: `notes/briefs/town-atlas-pages.md`.

### What changed
- The kept pictures' PNG pages are now packed the way the WebGL atlas packs (`paint.ts` `ATLAS`: 2048 px pages, 2 px padding, a picture over 1024 px alone; manifest v2). On a repeat visit, each decoded page goes into one atlas layer in a single upload (`paint-gl.ts` `adopt`, uploaded by `kept`). The 1,912 pictures are no longer cut out and uploaded one at a time.
- Each picture is now a stand-in canvas. It stays empty until something reads its pixels (hit tests, statue masks, through its 2D context) or the painter has to upload it alone (after a lost context, or `changed`); then it's cut from its page (`keep-pictures.ts` `domPageIO`). The decoded pages stay in memory until the town closes, about the same memory the cut canvases used to take.
- `TOWN_PICTURES.pagePx` is removed: the page size is the atlas's now.
- Fixed on the way: the painter kept its framebuffer across a lost context, and after a restore it pointed at a dead one (`readFb`).

### Measured (headless Chromium, software WebGL, repeat visit, tap to first frame, 4 runs each, main and branch back to back)
| | main | this branch |
|---|---|---|
| 4x slowed | 5.42–5.59 s (median 5.47) | 4.42–4.81 s (median 4.52) |
| 4x, the load itself | 3.05–3.35 s | 2.32–2.60 s |
| 1x | 2.15–2.40 s | 1.61–2.27 s |
| 1x, the load itself | 0.87–1.09 s | 0.66–0.85 s |

At 4x, cutting is gone (−1.15 s), but whole-page uploads add +0.35 s: about 50–65 ms a page here, because the browser converts each bitmap on the main thread. That's why the saving is ~1 s, not the brief's estimated ~3 s. Ideas I measured and didn't use:
- Decoding in workers: slower. The browser already decodes `createImageBitmap` off the main thread.
- Raw-byte uploads: about 3× quicker in a bench (6 / 19 ms a page), but they need a new storage format. A possible follow-up; see the decision note.

### Player-visible
- Nothing looks different; a repeat visit to the town loads sooner.

### Checks changed (old → new; none removed)
- `__townPictureSum()` (the guard hash in `e2e/perf.spec.ts`, "a second visit…"): it hashed the pictures' canvases; now it also returns `gpu`, a hash of what the atlas holds for each picture. The spec's `toEqual` therefore also compares the GPU side across the three visits (first visit, second with kept pages, third painted without workers). The spec file itself is unchanged.
- `e2e/town-street.spec.ts`, "the town's loading screen…": it checked zero uploads while walking on both visits; it still does, and now also loses the WebGL context on each visit and checks that every picture uploaded again holds the same texels as before.
- `town-keep-pictures.test.ts`: the packing test now checks the atlas layout (pages no bigger than the atlas's, padding clear, big pictures alone). Restore is tested for its pages and its stand-ins. Two new odd-entry cases: a v1 entry and a page bigger than the atlas's.

### Run locally
- `npm run typecheck`, `vitest` for app + core (3,385 passed).
- `e2e/town-street.spec.ts`: "loading screen" (phone) and "context lost" (both projects) pass.
- `e2e/perf.spec.ts` "a second visit…" @perf passes: second visit 4.58 s, 5.1 reference jobs against a bound of 6; canvas and GPU hashes the same on all three visits.
