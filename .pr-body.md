Schema run: once per instance, 4 round trips (the slow first load after a schema change)

## What changed
- **For players:** the first load after a deploy that changes the database schema no longer sits on the "HunChess" splash for seconds. No new text, nothing moves.
- `ensureSchema` (`packages/server/src/accounts.ts`) runs **once per Worker instance**: requests that come while it runs wait for that one run (5 s at most, then one of them runs its own: a run whose request was cut short never finishes, as `access.ts` found). A failure fails the requests waiting on it; the next request tries again.
- The run is 4 round trips: the version read (`meta.schema`; a current database stops here); the `CREATE … IF NOT EXISTS` statements and the ledger's triggers in one batch; every column of the tables that gain some in one read; then the missing columns (with their `then`), `AFTER_COLUMNS` and the version write last, in one batch. Same statements, same order; the identities rekey still runs when needed (2 more trips). A refused batch falls back to one statement at a time, as before (a trigger refused is logged and the database still loads; a column another instance added first is fine).
- The locker's `color2` migration joins `COLUMNS` (added if missing, instead of an ALTER every run that fails as a duplicate). This changes the schema fingerprint, so this PR's own deploy runs the new path once: a live check.
