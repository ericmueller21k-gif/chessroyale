## Cause
On the Boss Battle screen the app fetches the opening library in the background (`solo.ts loadOpenings`). The e2e server (wrangler's dev proxy, which retries once) dropped that request, so Vite fired `vite:preloadError`, and `stale.ts` reloaded the page as if a deploy had landed. The reload lands on home, because the Boss Battle screen isn't in the address. With that one file refused, main fails 2 of 2 with CI's exact error. Nov 23's lost Resume tap had the same cause (`2026-11-23-resume-race.md`). A player on a patchy phone connection was thrown home the same way.

## Fix (the cause, not the test)
- `stale.ts`: takes Vite's event every time, then asks `/version.json`. If the server runs another build (a deploy), the page reloads as before (once a minute at most, back where it was). If it runs the same build, or there's no answer within `APP_CACHE.staleCheckMs` (5 s, settings.ts), the load just fails and its caller tries again (Chrome fetches a failed module again: checked).
- `solo.ts loadOpenings`: a second try straight away, so a START that joined the failing background load still plays.
- `App.tsx startSolo` / `startTowerFloor`: a load that rejects says "Couldn't load the game. Check your connection and try again." (the existing line) instead of staying stuck on loading. This was Nov 23's follow-up.
- `lazy-game.ts`: marks `<html data-match-chunk>` only once the chunk is actually in.

Player-visible: no new text. A dropped file no longer reloads the page. A real deploy still does.
