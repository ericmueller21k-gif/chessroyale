Addendum for the PR (the town flake the director added, Nov 19):

**`e2e/town.spec.ts:221` (old tab after a deploy), not fixed; the director gave it about 20 minutes and said to leave it if the cause wasn't clear.** What I found:
- It reproduces locally under load: 1 of 6 failed with `--workers 3`, the same `next: false` at line 246.
- On CI (run 44467157290, shard 2), both tries got past the caches check: the next version's cache `brc-ffffffffffff` existed. So the next worker's install **started**. Only `next` (the controller being /api/e2e/sw.js and `activated`) stayed false for the whole 60 s.
- The code rules out a slow install or activation. Install needs no network: every one of the 58 non-/assets/ files in FILES has a hash, and the old cache holds each one hash-tagged, because runtime caching only stores pictures and /assets/ files. Activation waits at most 1.5 s per tab (askEntry). #812 touches nothing here, and the app registers /sw.js only once, at load, before the controller exists, so there's no register race.
- I logged the registration's states in 9 more runs under the same load: register resolved, then installing → installed → activating → controllerchange → activated within about 0 to 2.5 s each time, and none failed. So when it works, it isn't slow. A failure is all or nothing.
- My best guess, unconfirmed: the next worker's install or activation **threw**. Its install throws on any non-ok fetch, and if the worker goes redundant, nothing retries and the test can't see it. The test uses `void navigator.serviceWorker.register(...)`, so a rejection or a worker gone redundant leaves only "next: false". Next step: keep the registration's state log and the `register` rejection in the poll's message (a small spec change) so the next failure names the stage. Or run `--repeat-each=20 --workers 3` with that log to catch one.
