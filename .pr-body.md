# Load regression: /api/me in 4 D1 round trips (was 28); a gentler precache that keeps what didn't change

**What changed**
- **`/api/me`**: `profile()` read 28 D1 rows one after another (about 40 ms each from a Worker: the live 1.1-1.7 s). Its parts (results,
  chat standing, shop, locker, ranked, XP, leaves) now read at once, and so do the reads inside each helper; the session and its account
  are one read (`userFromToken`). The Welcome Crate's grant still lands before the locker's holdings are read.
- **`/api/quests`** and **`/api/friends`**: their reads at once too. **App**: `loadAccount` asks for `/api/me` beside `/api/auth/config`, not after it (one round trip less before home knows you).
- **Service worker precache**: one file at a time at low priority (was all 127 at once right after a first visit's load), and after a
  deploy it copies files an older version keeps unchanged (same name under `/assets/`, else the same hash: new `HASHES` in `sw.js`).
- **Manifest** fetched with credentials (`crossorigin="use-credentials"`), so Access stops 302ing it (Eric's CORS error).

**The brief's three questions**
1. `/api/me`: the 28 sequential reads above. Fixed.
2. DOMContentLoaded 5 s: not from the main thread (0.5 s at 4x CPU). Chrome starts a new version's install only once the page settles,
   so it never delayed home itself; it delayed what came next (the precache above), on a first visit and after every deploy.
3. The 30 s white page: a cold first paint waits only for the page and its 90 kB of styles; page loads never reach our Worker
   (`run_worker_first` is `/api/*` and admin), and the worker registers after load. Most likely Cloudflare Access signing in again (the
   manifest's 302 shows Access in front of every file). If it happens again: DevTools Network with "Preserve log"; a 302 to
   `cloudflareaccess.com` first would confirm it.
