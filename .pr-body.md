Fixes main's FLAKY_RED at d4cf40be: `[phone] xp.spec.ts:223` ("each other No XP line") waited 4 min for Boss Battle's START on home (run 45559755980, shard 10).

## Cause
- On the Boss Battle screen the app fetches the opening library in the background (`solo.ts loadOpenings`).
- The e2e server (wrangler's dev proxy, which retries once) dropped that request. Vite fired `vite:preloadError`, and `stale.ts` reloaded the page as if a deploy had landed.
- The reload lands on home, because the Boss Battle screen isn't in the address. With that one file refused, main fails 2 of 2 with CI's exact error.
- Nov 23's lost Resume tap had the same cause. **A player on a patchy phone connection was thrown home the same way.**

## Fix (the cause, not the test)
- **`stale.ts`:** takes Vite's event every time, then asks `/version.json`.
  - The server runs another build (a deploy): the page reloads as before, at most once a minute, back where it was.
  - The same build: the first failure just fails and its caller tries again; a second failure reloads (see "Older Chromium").
  - No answer within `APP_CACHE.staleCheckMs` (5 s), i.e. offline: never a reload; the load fails.
- **`solo.ts loadOpenings`:** a second try straight away, so a START that joined the failing background load still plays.
- **`App.tsx` `startSolo` / `startTowerFloor`:** a load that rejects shows the existing line "Couldn't load the game. Check your connection and try again." instead of staying stuck on loading.
- **`lazy-game.ts`:** marks `<html data-match-chunk>` only once the chunk is actually in.
- **`vite.config.ts`:** the build also takes its commit from `GITHUB_SHA`. CI's containerized build had called itself "dev", which never sees a deploy (town.spec's staged deploys).

## Older Chromium
- **CI failed `xp.spec.ts:476` both tries at f09c6110:** Boss Battle with "Couldn't load the game.". The page didn't reload, but the try again of the refused file failed too.
- **Cause, checked:** Chromium 141 (CI's Playwright 1.56.1, build 1194) keeps a failed dynamic `import()`. A re-import of the same URL fails without fetching: 3 imports gave 2 server hits. Chromium 158 fetches each time. Safari keeps failures too. So on those browsers a try again (and `lazyGroup`'s "next time") could never load the file until the page reloaded.
- **Fix:** a second failure while the server answers with this same build reloads the page (the same once-a-minute limit as for a deploy). Boss Battle is now a place (`App.tsx`: `setPlace` / `takePlace("raid")`), so the reload lands back on it, never home. `takePlace` takes the screen's key (the town's is `"town"`), and `dropPlace` clears only a screen's own place.
  - In a newer browser one dropped file still never reloads: the try again fetches it.
- **Why not a fresh URL (`?retry=1`):** it needs the failed URL from the error's text, which Safari leaves out, and it can't fix a failed shared chunk that the module imports. A reload clears every kept failure in every browser, with less code.

**Player-visible:** no new text. A dropped file no longer sends you home: a newer browser just tries again; an older one reloads once, back on Boss Battle. A real deploy still reloads.
