# PR #610: the independent review's findings, and what was done

- **B1** (e2e red: the reviewer banned in `e2e/fairplay.spec.ts`): fixed by the director (2970b78); this round only changes the
  refusal's text the spec matches (`/^a ban is for a person/`). Passes locally on phone.
- **M1** (the ban bar rests on the judges' numbers; the reviewer's token could ban an honest player there): step 4, the director's
  call. The reviewer's token never bans: `decide` answers 409 "a ban is for a person…" to any reviewer ban, before anything else
  (`fairplay.ts`). Unit (`fairplay-admin.test`, `review-b2.test` "M1: end to end", now refused outright and a person bans) and e2e
  updated; `docs/fairplay-reviewer.md` (the API takes clear, watch, review; "Review, for a person to ban"; check "hard" finds
  yourself), the area page and the settings comment. Steps 1-3 not built: a ROADMAP line under fair play, and the decision note says
  bans stay off until they land. The review's first M1 test is kept as the known limit it shows.
- **m1** (a retried fair-play write never acts): on a retry whose row went in, `recordFairPlay` still queues the deep re-check (when
  flagged) and runs `actOn`. The retry weighs the match once: the history read leaves out this lobby's own row, and on `!added` the
  level is worked out from what's stored (`levelNow`, as `relevel`), so a person's decision since counts. `review-b2.test` "m1":
  review opened, deep re-check queued, the same score and level as the control's.
- **m2** (every event waited on the write before arming the alarm): `persist` arms the alarm and dispatches the engine queue, then
  writes in the background (`ctx.waitUntil(this.writeResults())`). No re-arm after the write: the alarm armed first is already the
  results' next try (a second on), which finds the write done or shares it; re-arming with the event's own core could put back a
  stale match time. `review-b2.test` "m2": the alarm is set while D1 still waits; once D1 answers, the result goes in once.
- **m3** (lenient by tries): by time. `PendingResult.failedAt` (first failure); lenient `MATCH_SAVE.strictMinutes` (30) after it.
  `match-end-save.test` updated (five failed tries in the window still hold; past it, the result goes in).
- **m4** (the deep re-check's throughput): `searchPosition` (shared with 1 v 1's check) takes a position's whole budget in one
  conditional update before its first search (all or none); a server that stops answering gives back the searches it never made.
  Outside a review, a match is checked to `levels.banMatchChecked` (8) counted moves, then leaves the queue undone; `setCase`
  (review) queues it again. `dailySearches` unchanged. Two new tests in `fairplay-deep.test`. A banned case is capped too (the brief
  said "unless in review"); say if appeals should get the full check.
- **m5** (engine cap): the app treats 401 and 429 like 404 for the rest of the game, and the game's ping can set it; a new game asks
  again (`app/src/engine.ts`; new `app/test/engine-server-refusal.test.ts`). Solo's limit is `soloCap(cap)` =
  min(`soloDailySearches`, `soloShare` (1/3) of `ENGINE_DAILY_SEARCHES`) (`engine-server.test`). Not measured against a keen solo
  player: said in the PR body.
- **m6** (Welcome Crate): a solo game counts with `XP.minMoves` (10) moves and `WELCOME_GIFT.soloMinSeconds` (60) of the server's
  time, not 3 minutes, so it follows XP's own rule (which the result screen explains). Old untimed rows left as is (PR body).
- **m7** (the token can still put an account in review): one line in the decision note.
