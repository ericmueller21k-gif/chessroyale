# An open tab survives a deploy (Nov 15, 2026)

**Eric (Nov 15, on a computer):** "I clicked on a different tab, and then I went back ... challenged Wrangler the Pig ... hit challenge
alone fight. And then it reloaded the town and put me back in the center." His tab ran 018bd310; #724's deploy had gone live three
minutes before. The challenge's chunks (`shops/intro.ts`, `shops/ShopRoom.tsx`) were gone from the server, and from the device: the new
version's service worker deleted every other version's cache as it took over (`activate`). `stale.ts` reloaded the page, and the
prevented `vite:preloadError` made the imports resolve `undefined` first ("reading 'loadIntro'" of undefined in the ops errors).

**What changed:**
- The worker keeps each version's cache while a tab runs it. A tab is matched to its version by its entry script
  (`index-*.js`, which only the caches of that version hold): the worker asks every tab (`brc-entry?`, `install.ts` answers on the
  message's port) as it takes over and on each page's load (`brc-loaded`). A tab that doesn't answer in 1.5 s keeps the newest
  `APP_CACHE.keepVersions` (3): background tabs can be frozen, and tabs from before this don't answer. Storage: an old version goes
  once no tab runs it, at most 3 kept while a tab is silent.
- Requests: under `/assets/` from any kept cache (Vite's names are their contents' hash, so a name is one file whichever version);
  any other file only from this version's cache (`/engine/…`, sounds, `/`: one name across versions, never an older copy for a new
  page). Not kept from the network: a `text/html` answer for a file (the SPA fallback's page for a missing file).
- `stale.ts`, still the fallback: the screen says where you are (`setPlace`), kept in session storage across the reload and read once on
  the next load (`takePlace`, only at the same address). The town starts at your square and facing and opens the room or challenge
  (a challenge from where you stood as you called it, so you walk up with the boss again). Calls made: a door between two rooms, and
  a challenge called inside Don Dough's, come back as the home's front room (the inside challenge is a tap there again: simpler than
  rebuilding his back room's state). The minute rule stays: a second miss within it isn't reloaded, so nothing is kept to reopen.
- `chunk()` (stale.ts) on every `import(...).then(...)` in the app (not `lazyGroup` or the Colosseum page, which already check): an
  import Vite gives as `undefined` (the page reloading) never settles, so nothing throws or backs out first.
- Not covered: a picture under `/assets/` changed by the deploy and never shown before it (pictures aren't precached, Nov 10). Rare
  (pictures keep their names unless they change); it fails as today.
- The e2e needs a deploy with a service worker in charge, and the browser fetches a worker's script past Playwright's routes (tried:
  `context.route`, the SW network events flag, a browser-level CDP `Fetch`). So the e2e server serves "the next deploy's worker" at
  `GET /api/e2e/sw.js` (`e2e-sql.ts`: only where `E2E_SQL` is set, with its key in the query, as a script fetch can't carry headers).

**Also (the Safari error `undefined is not an object (evaluating '[d,f,p,m]')`, 7453120ed891):** `RideLayers` (Items.tsx) reading the
seat of idle frame `f` of a ride with fewer frames. `useIdleFrame` kept its frame number for one render after a riding avatar changed
ride (another player's in the same place, a ride put on). The frame now carries the ride's times it counts, so a new ride starts at 0.
