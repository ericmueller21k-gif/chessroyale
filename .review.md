# Review: `claude/chandy-move-mix` (a4ca7e0) against `origin/main`

Boss lane, one read-only pass. Read: the diff, the full turn flow in `packages/chess/src/bosses/chandy.ts` (afterCrowdMove,
firstLock, afterHisMove, passive/landMove, queenLockDue/applyQueenLock, setUp), the runner's `bossMoveMoment`, the lobby's hold
(`playBoss` / `bossPlay` / `thinkMinAt`), solo's `beforeShow`, `chandyTurnMoments`, `chandyTurnMs`, the FAQ and area page.
Ran `packages/chess/test/chandy.test.ts` (46/46 pass) plus a throwaway probe (not committed).

**No blocking findings.** Everything the brief asked about checked out:

- **Solo vs. online:** `fired` and `marked` live only in the server's/runner's `ChandyState`; nothing on a client or the host
  recomputes the meter (`meterPick`/`meterOrder`/`unlockPick` aren't used in `packages/app` or `packages/server`), and the view
  doesn't need them. The host's steering stays `steer()` → null until `taught`, the same function both ways. The second taught
  capture goes through the same `bossMoveMoment` → `firstLock` path solo and online. On the lobby's re-entry from `bossPlay`,
  `firstLock` returns null (the mark is already in `locks`), so the move isn't held twice. The parity test's
  `firsts.length === teachCaptures` would catch an online path that skipped the second mark.
- **Reset between battles:** `opening.setUp` builds from `FRESH`, which has no `marked`/`fired`. `fired()` and `afterHisMove`
  always spread, so the shared `FRESH` is never mutated. `?power=dodge` sets `taught` with `marked` unset (fine: `taught` gates
  everything).
- **The second taught capture:** probed with en passant (`d4e3` after `e2e4`: the mark goes on e4, the pawn's square, and
  marked 2, taught, upgrades 2) and a promotion capture (`b2a1q`: the mark is on a1; the same result). Before `taught`, no hunt
  lock can exist (`passive` requires `taught`; `afterHisMove` drops any mark his move didn't take), so "a capture of an
  already-locked piece" can't double count. Strike, slip and `?power=lockon` moves all go through `ordinary()` →
  `bossMoveMoment`, the same as the first capture.
- **The queen lock as his first unlock:** `queen` is read from the board *after* his move, so taking the crowd's queen with
  that capture gives the usual random unlock (the test covers it; the probe agreed).
- **`fireOnUnlock` with the new order:** upgrades 1 and 2 on back-to-back turns work: unlock 1's `due` lands at the next
  `passive`, `fired()` keeps `fresh` = unlock 2 (it only clears `fresh` when it equals the fired move), and unlock 2 fires
  on the following turn. If the pass guard refuses the queen lock, `meterPick(…, ["queenlock"])` uses the same order.
- **The meter order:** `seeded` (rolled per move) and then a stable sort by (is last, fired count) match the rule. `landMove`'s
  fallback demotes the last-fired move but still tries it last, which fits "never while another can come". The three new meter
  tests and the seeded battle would fail on main's random pick.

## Low (for the director; no fix needed to merge)

1. **Low: the queen lock as the first unlock can still leave the early slot dead.** `chandy.ts:1135`
   (`afterHisMove`, `queen = …some(type === "q")`) and `chandy.ts:1078-1085`. The decision says "it never wastes an early
   slot", but that only holds when the crowd has no queen. Scenario: the crowd still has a queen, but `queenLockOk` is false
   (no pawn/knight/bishop can block, or the pass guard keeps refusing). The queen lock is his only unlock, so
   `meterPick(c, seed, ["queenlock"])` returns null every turn, the meter sits full and nothing fires until upgrade 2. The
   sim's "aimed in 14 battles of 20" suggests about 6 of 20 battles where the first unlock never fired. With `teachCaptures`
   2 the gap is short (upgrade 2 at a median of 11 crowd moves), so this is a product call, not a bug. Suggested fix, if
   wanted: force the queen lock only when it could come now (e.g. `queenLockOk(boardOf(b).fen …)` with him to move, at the
   unlock), else the random unlock. Or just reword the decision line.
2. **Low (test gap): a queen shot and a taught capture's lock in the same turn is new and untested.** Before, the queen lock
   needed an unlock and the first unlock came with `taught`, so `queenShot` and `lockOn{first}` could never share a turn.
   Now it's likely: upgrade 1 unlocks the queen lock, it aims, the shot fires as his next turn starts, and that turn's move
   can be his second capture. From reading the code, the order holds everywhere: solo waits `thinkEnd` (which includes
   `chandyTurnMs`) before `beforeShow`; the server holds to `thinkMinAt`, then re-enters `playBoss` and adds the 900 ms lock
   hold from then; `chandyTurnMoments` puts the lock after the shot. Nothing pins it, though. Suggested: one focused case in
   `chandy.test.ts`, or the parity test on a seed where it happens: the shot's event before the `first` lockOn on one
   `turn`, and online `bossMinAt` ≥ the shot's end + `CHANDY_FX.lockOn`.
3. **Nit: stale "first capture" comments** (one-word fixes, docs only):
   - `chandy.ts:1091-1094`: the `firstLock` docstring, "His first capture … null: not his first capture". It is now each of
     the first `teachCaptures`.
   - `packages/core/src/boss.ts:1092`: "`taught`: his first lock has come".
   - `packages/server/src/lobby.ts:2715`, `packages/chess/src/runner.ts:1637`, and `packages/app/src/components/Chandy.tsx:6`
     and `:201-203`: "his first capture" or "his first lock".
4. **Note: queen-shot captures don't teach.** A queen shot that shatters a piece between capture 1 and capture 2 isn't
   counted as a taught capture: no mark, no upgrade. That matches the header ("his engine's own moves"), so it isn't a bug.
   Worth one line to Eric if he reads "his 2nd capture" to include the shot.

No checks were changed or removed by this review.
