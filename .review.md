## Major

### M1. A floor under way keeps a boss its kill switch has since rested, and leaving it counts as a loss

`packages/server/src/tower.ts:249` (`under` answers the stored bosses whatever the pool says) with `:323-325` (`stopTower`: the
device's `moves` alone decide free or counted).

A kill switch (`PAUSE_BOSS_<id>`) is how we take a broken boss out of play. In the tower, a floor already under way keeps that
boss: a reload rejoins it (the design's restore) and plays the broken boss again. The only way out is Stop, which after your 2nd
move ends the run. So one ops action can cost a player a 40-floor climb through no fault of theirs. This is also how a boss that
leaves the roster in code (a rename or removal) plays out for a run caught mid-floor: the `under` answer's `settings.bossIds`
names a boss the app doesn't have.

**Failing case (run):** a run's floor 1 under way with `gingerbread` → `towerPool(["gingerbread"])` (its kill switch on) →
`POST /floor/start` answers `200 { under: true, bosses: ["gingerbread"], settings.bossIds: ["gingerbread"] }` →
`POST /stop { fight, moves: 2 }` answers `{ stopped: "lost" }` and the run is out.

**Fix (small, server only):** in `stopTower`, take the stop as free when the floor's bosses no longer pass the pool now:
`sideRefusal(floorBosses, opts.pool)` non-null → `leaveFloor(before, 0)`. That's "our pause, not your leave": the same floor is
dealt again at the next start, because `startFloor` already re-deals a refused floor. Mark it in the `under` answer too
(`resting: true`, or the ids) so PR 10 can offer "Leave (free)". A player can't flip a kill switch, so this opens no dodge. The
floor stays playable: a device that can still play it finishes as now (the "a match running finishes" rule holds). Add one test
next to "a boss resting since the deal…".

## Minors

**m1. A retried result after a lost answer can't tell "taken" from "refused", and the 409 carries no state.**
`tower.ts:289`, `:302` (409 `{ message }` only); `:293-304` (the CAS, then `soloBest` as a separate statement). A phone sends
`won`, the server applies it, and the answer is lost on the network, or `soloBest` throws after the CAS has committed (a 500).
The retry gets `409 "That floor isn't under way."` (run: exactly that body), though the floor was won. The data is right; the
device is told nothing useful. Fix: put `run` (the open run's view, or null) and `best` in finish's 409, as `stopTower`'s 409
already does with `run`, so the app recovers in one trip. Better still, keep the last finished `{ id, outcome }` in the row and
answer a same-id, same-outcome replay with the stored result. Either way PR 10's contract: a 409 on finish means "read the run
again", never "error". (A retried counted stop already answers `between` with `run: null`, which does show the run ended.)

**m2. The privacy policy's "kept" line is wrong for a replaced climb.** `Legal.tsx:235` says "a climb until you start your next
one". But `newTowerRun` with `confirm` (`tower.ts:205-206`) deletes only runs that had already ended and marks the replaced one
`abandoned`, so a replaced climb is kept until the run *after* the next one. The test "replaces an open run only with confirm"
asserts exactly that. The same applies to the run a sign-in merge abandons. Fix: in the confirm batch, delete the replaced run
after `soloBest` (its floors are counted first) instead of abandoning it, keeping `abandoned` for the merge only. Or reword the
line, the area page (`battle-tower.md:86`) and decision 3. A policy line should match the code exactly.

**m3. A solo best is 10 seconds a floor of the device's word.** `settings.ts:1295`, `tower.ts:290`. A script climbs all 99 floors
in about 17 minutes. The design accepts the device's word for solo (as Boss alone), so this isn't a defect today. Elsewhere,
though, a solo win that pays needs `XP.soloWinMinMinutes` (5) of the server's time. Keep solo `tower_best` off any leaderboard and
out of anything that pays (the design already marks solo emblems "solo"), or raise the bar by floor before it shows anywhere
public. A line in the decision note would make that a recorded call.

**m4. A run whose `met` doesn't parse is stuck "resting" for good.** `tower.ts:132-141` turns bad JSON into `floors: []`, so
`startFloor` answers null and the route answers `503 "The tower's bosses are resting…"` forever (run: the probe). GET then shows
floor 0. Only this code writes `met`, so this is unlikely. Cheap guard: answer `409 { message: noRun, confirm: true }` instead,
so the app offers a new run.

**m5. Lowering `BATTLE_TOWER.floors` below a live run's floor.** Core's `finishFloor` (`floor >= s.floors` → top) then marks a run
on floor 60 "top", and `soloBest` (`tower.ts:173`, `CASE WHEN status = 'top' THEN floor`) records a best of 60 with a top of 50. A
settings edge, not today's numbers. Either cap the best at `BATTLE_TOWER.floors` or note on the setting "only ever raised".

**m6 (tiny, fine to leave).** `tower_best.at` on the repair path is the run's `updated_at` (`tower.ts:172`), not when that floor was
won. The merge copies the guest's best rather than working it out from the runs it moves (`:390-395`), so a guest best that missed
its write stays low until the account's next result or run. Both heal themselves.

**Notes for PR 10 (the app), not defects here:**
- Two confirmed new runs at once both answer 200. The losing tab holds the view of a run that's now abandoned. Harmless, because
  every route acts on whichever run is open and the fight id guards results, but the app should show the run each answer carries.
- Opening the tower on a second device while the first plays: `start` answers `under` with the same fight. Per the design, a
  device with nothing to restore counts it lost, so ask first ("This floor is under way on another device") before sending the
  counted stop.
- `beaten` (and the download's `floors`) can name a boss later renamed or removed from the roster: draw unknown ids safely.

## Checked, fine

- **Schema:** `TOWER_SCHEMA` sits in `SCHEMA` (all `IF NOT EXISTS`), so the version fingerprint changes and `schemaRun` makes the
  tables once per database. Fresh and upgrade both pass on real D1. The partial unique index `(user_id, kind) WHERE status = 'open'`
  is accepted and enforced (the race probe). `openRow`'s `status = 'open'` matches its WHERE word for word. Both upserts from a
  `SELECT` carry a `WHERE`, which avoids SQLite's `ON` parsing ambiguity. `tower.ts` imports only types from `accounts.ts`, so
  there's no runtime import cycle. `account-data.test.ts`'s schema pin was updated.
- **Routes:** behind `userFromToken` (a guest's cookie as anyone's; no session → 401); the API rate limits and the ban gate run
  before any route (`index.ts:164-186`). The session cookie is `SameSite=Lax`, so a cross-site form can't post `{confirm: true}`.
  Unknown tower paths and methods → 404. `kind` other than solo → 400.
- **The seed is the server's** (`crypto.getRandomValues`; the body's `seed` is ignored: the API test). The pool is
  `towerPool(pausedBosses(env))`. PAUSE_SOLO refuses a new run or floor and lets one under way answer, finish and stop.
- **One result, once, for the floor started:** finish and stop are one `UPDATE … WHERE id AND status = 'open' AND fight = <as read>`.
  - A replay, a second tab, a stale stop or a stale finish after a free leave and a restart all get 409, or "between" when nothing
    is under way.
  - Start is a CAS on `fight IS NULL AND met = <as read>` with a re-read, so two starts answer the same fight.
  - New run against finish: the finish's CAS needs `status = 'open'`.
  - Merge against an in-flight finish: the finish lands on the moved row (no `user_id` in the CAS), and the account's best heals on
    its next result.
  - Delete against a finish: the finish matches no row.
- **No skipping, no undoing a loss:** each result moves the run one floor, and only for a fight the server started. No statement
  ever sets `status` back to `open`. A new run starts at floor 1. A free leave brings back the same bosses (no re-roll) unless a
  kill switch changed the pool. A win sooner than the minimum is refused with the floor still under way.
- **Floor 99:** `top`, best 99, no floor after it (the test, and core's `finishFloor`).
- **The best:** the highest floor won (`floor - 1`; 99 for the top), worked out again from every solo run before ended runs are
  deleted (`soloBest` first in the new-run batch) and after each result, and only ever raised. Abandoned runs count their floors
  won.
- **The sign-in merge** (guest → account only, in the one batch): bests take the higher; the guest's open run is abandoned if the
  account's floor is at least as high; then the account's if the guest's is still open; then everything moves. So there's at most
  one open run per kind before the move, and the unique index can't fire. A guest's floor under way survives when its run wins
  (real D1 probe). A second sign-in at once finds nothing to move.
- **Download:** kind, floor, status, the floors' bosses, the fight's start, started/updated, and the bests. No seed and no deck.
  The floor about to be fought is already in GET.
- **Delete:** `towerDeletes` is in `ACCOUNT_STORES`, so it runs in `deleteAccount`'s one batch, which also serves test accounts
  (`test-accounts.ts:151`). There's no other path that deletes accounts or prunes guests.
- **Core's deal in `met`:** a stored floor that the pool, `apart`, `maxBosses` or the roster no longer allows is re-dealt at start
  (a renamed boss: run). Unknown ids drop out of the deck. A floor that was dealt keeps its boss count if `pattern` changes. `decks`
  and `seed` keep a re-deal reproducible. GET's between-floors view re-deals without saving, and start saves the same deal under
  its CAS. The only rough edges are M1 (a floor under way) and m5 (lowering `floors`).
- **e2e:** `account-delete.spec.ts` gets `TEST_SWITCHES:1` from `playwright.config.ts:48`, so its immediate win is taken; the new
  tables are in its "nothing names the account" list. The `areas.json` entry is right. The PR carries `full-e2e`, and its CI
  hadn't finished when I looked.
- **Docs:** the area pages and the decision note match the code, apart from m2's line.
