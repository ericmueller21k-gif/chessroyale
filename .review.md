## Minor

### 1. M1: the stop decides "free" when it arrives, not when the app was told `resting`

`tower.ts:365` (`floorResting(before, opts.pool)` at the stop) with `:293` (`resting` only in the `under` answer). PR 10 will offer
"Leave (free)" from an `under` answer that said `resting: true` (the area page's "For PR 10" says so). If the pool changes back
before the tap, the stop counts:
- the kill switch is turned off (a dashboard change deploys a new version within seconds), or
- during that deploy, the stop lands on an instance still on the other version (`kill-switches.ts`: switches are read per instance).

`leaveFloor` then takes the device's real `moves`, the player gets "lost", and the climb is over. The answer that offered a free
leave isn't held to. The odds are low (it needs an ops change inside the seconds between the answer and the tap), but the cost is
a whole run, and it can't be undone (no statement sets `status` back to `open`).

**Failing case:** floor 12 under way, its boss rested → reload → `start` answers `{under: true, resting: true}` → ops turns the
switch off → the player taps "Leave (free)" → `POST /stop {fight, moves: 14}` answers `{stopped: "lost"}` and the run is out.

**Fix (server, a few lines):** the stop takes `free: true` (the app sends it when it offered a free leave). When the leave would
count, answer 409 `{message, fight, run}` and write nothing, so the app can ask again on the real terms ("That boss is back: leave
now and it counts as a loss"). This opens no dodge. A refused stop leaves the floor under way, as if the player hadn't tapped,
which they can always do. Add a line to the area page's "For PR 10". (Another option: once a start finds the floor resting, keep
it free in `fight`. But that's a write on the `under` path, so I'd take the `free: true` check.)

### 2. m4's guard isn't on the stop: a stop on a broken deal writes `floor = 0` over the run's floor

`tower.ts:357-375`. Start (`:269`) and finish (`:316`) answer `BROKEN`. The stop doesn't. With `met` unparseable:
- `runOf` gives `floors: []`;
- `floorResting` is true (`sideRefusal([])` refuses: none of 1 to 3 bosses);
- `leaveFloor(before, 0)` returns the run as is;
- the CAS writes `floor = 0` and `met = {"floors":[],…}`.

Real D1 probe: a run on floor 5 (4 won), `met` broken, its best's write missed, then `stop {fight, moves: 12}`:
- the answer: `200 {stopped: "free", floor: 0, run: {floor: 0, bosses: []}}`;
- the row: `floor 0`;
- the confirmed new run after it: no best at all. The 4 floors won were lost to `soloBest`'s repair, and the download would have
  shown floor 0.

It needs a broken `met` (only this file writes it) and a missed best write, so it's very unlikely. But it's the one route m4's fix
didn't reach. **Fix:** `if (!before.floors.length) return BROKEN;` after `runOf(row)` in `stopTower` (as finish does), and one
line in the test "a run whose deal doesn't parse".

## Nits

- **"Your last floor's result" (privacy policy).** Only finish writes `last`, so it's the last result your device sent. A run
  ended by a counted stop keeps the floor before's win as its `last`. Its download shows `status: "out"`, `floor: N` and
  `last_result: {won, floor: N-1}`. The status and floor tell the truth, but the line reads as if `last` were the stop's loss. Fine
  to leave. Or word it "the last floor result your device sent" (`Legal.tsx:230`). Separately, `account-data.ts:143-145` (the tower
  store's comment) doesn't list the last result yet.
- **`last` lives only in `CREATE TABLE`, not in `COLUMNS`.** That's right for every real database. Main has no tower tables (it's
  at `dbc4ec7`, before PR 9), production deploys only from main, staging is built and torn down for each load test, and CI's e2e
  uses a fresh temp folder (`playwright.config.ts:19-31`). The probe confirms a database that ran `a08cad4`'s schema stays without
  `last` after this head's `ensureSchema` (the version changes, and `CREATE TABLE IF NOT EXISTS` is a no-op). So only a local
  `.wrangler` state kept from `a08cad4` (`E2E_KEEP_STATE=1`, or `wrangler dev`) would 500 on the tower routes. To fix one, delete
  that state. No action needed.

## Notes (no change asked)

- **M1 gives a player a free option, bounded.** A floor under way whose boss is rested mid-floor can be played on: a win counts,
  and if it goes badly the player can leave free, as long as the device hasn't sent `lost`. No player can cause it:
  - core's deal tests (`packages/core/test/tower.test.ts:99-137`) hold every dealt floor to `sideRefusal(bosses, pool)` under the
    same pool, so `floorResting` is never true without an ops or code change;
  - the pool is `towerPool(env.off)`, from environment variables and the static roster, not per user or per clock;
  - `isPlayable` has no dates;
  - a modified client could already claim `moves: 0`.

  It's one floor per affected run, because the free stop's re-deal drops the rested boss. That's acceptable. Decision 11 could
  name the trade in a clause ("a resting floor is a free option until it's left or finished").
- `resultAgain` answers a replayed result with `status` as it was then, and with `run` as it is now (e.g. `status: "open"`,
  `run: null` after a later counted stop). That's as documented ("answered as it was … with the run and best as they are now"),
  so PR 10 must take its state from `run`, as the area page says.
