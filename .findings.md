# Flaky fairplay.spec.ts "a ban means you can't sign in": findings (WIP, Nov 15)

## Reproduced
- Locally, phone, `--trace off`, one worker: failed 1 of the first 12 runs at the brief's step (`emailSignIn` from the
  "fresh browser" step, heading not found). With `--trace on` it passed 40 of 40, idle and under CPU load: tracing slows the
  page enough to hide the race. That is why CI's retry (`--trace on-first-retry`) always passes.
- (Two parallel repeats of this test fail for another reason: they share the project's one admin address. Not CI's failure.)

## What happens (request log of the failing run, ms from the test's start)
- 11427 reload with the planted session cookie (the "own sign-in cookie" step). The app's first three requests go together:
  `/api/status`, `/api/me?name=Banny`, `/api/auth/config`, all carrying the planted `hc_session`.
- 11712 `/api/status`: the ban answer (session ended, `hc_banned` set). 11758 `/api/me?name=Banny`: **200, a new guest session**
  (see the server race below). 11761 `/api/auth/config`: 200.
- 11763 the app (behind the ban screen) asks `/api/friends` with that guest session and the mark.
- 11766 the test clears cookies; 11768 clears localStorage.
- 11771 `/api/friends` answers: the ban answer, **`hc_banned` set again, and `brc.banned` written again** (ban.ts `enterBan`).
- 11779 `goto("/")`: the browser is marked again, so every route answers the ban; the ban screen, not the sign-in.
  At the failure: localStorage `brc.banned: "1"`, cookies `hc_banned`.

So the test's "fresh browser" is not fresh: the old tab is still running, and an answer to a request it sent before the clear
lands after it and marks the browser again. That answer is right (the request came from the banned browser, with the mark);
a real fresh browser has no old tab. CI's snapshots (main b6582a7f, #726's) show a guest home ("Player") rather than the ban
screen: the same race with another order (a late answer's JS flag write after the clear, its cookie before it), so the next
load starts from a half-cleared browser.

## For the director (server, ban gate: not changed here, full lane)
- **Concurrent requests with one banned session:** the first to reach the gate ends the session (`banAnswer` deletes it); a
  request already on its way with the same cookie then finds no session, so `banGate` returns null and the route runs as for a
  guest: `GET /api/me` makes a **new guest account and session** for the banned browser (200), `/api/auth/config` answers 200.
  The ban still holds (that browser's next request carries the mark and is refused, the new session ended), but each such race
  leaves a stray guest account, and the app gets a moment of a loaded guest profile behind the ban screen (here it asked
  `/api/friends`). A fix would be in `ban-gate.ts` (e.g. remember a just-ended banned token for a moment and answer it the ban,
  instead of "no session").
- **The app asks the API behind the ban screen:** account-driven requests (friends here) still go out while only the ban screen
  shows. Harmless (each gets the ban answer), but it's traffic and log noise from a banned device.
