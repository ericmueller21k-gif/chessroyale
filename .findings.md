# Flaky fairplay.spec.ts "a ban means you can't sign in": findings (Nov 15)

## The cause: the test (fixed on this branch)
The "fresh browser" step cleared the cookies and localStorage of the tab still open on the ban screen, about 50 ms after the ban
screen drew. That tab still had requests on their way. The answer to one sent before the clear (the ban answer: it sets the
`hc_banned` mark and the app writes `brc.banned`) landed after it, so `/` loaded in a browser marked banned again. The server and the
app were right: the request came from the banned browser, with the mark. A real fresh browser has no old tab.

Request log of a failing run (phone; desktop's is the same, the late answer 8 ms after the clear):
- 11427 reload with the planted session cookie: `/api/status`, `/api/me?name=Banny` and `/api/auth/config` go together.
- 11712 `/api/status`: the ban answer (session ended, mark set). 11758 `/api/me?name=Banny`: 200, a new guest session (the server
  race below). 11763 the app behind the ban screen asks `/api/friends`, with that session and the mark.
- 11766 the test clears cookies; 11768 clears storage. 11771 `/api/friends`: the ban answer. The mark and `brc.banned` are back.
- 11779 `goto("/")`: every route answers the ban. At the failure: storage `brc.banned: "1"`, cookies `hc_banned`.

Counts, locally, one worker: with `--trace on`, 0 failures in 40 phone runs (idle and under CPU load); with `--trace off`, 1 in 20
on phone and 1 in 20 on desktop. A trace slows the page enough that every answer is in before the clear, which is why CI's
retry (`--trace on-first-retry`) always passed. CI's two snapshots I read (main b6582a7f, #726) show a guest home ("Player")
rather than the ban screen. I didn't capture that exact order; it fits the same race with the late answer split across the clear
(its cookie before it, its `brc.banned` write after). The fix takes away the whole class: no answer to the old tab can reach a new
context.

## For the director: ban code, not changed (full lane)
- **A request with a just-ended banned session is served as a guest.** Several requests leave together with the banned session's
  cookie. The first to reach the gate ends the session (`banAnswer` deletes its row). The others then find no session, so `banGate`
  returns null and the route runs as for a newcomer: `GET /api/me` makes a **new guest account and session** for the banned browser
  (200), `/api/auth/config` answers 200. The ban still holds: the browser's next request carries the mark and is refused, and that
  session ends. But each race leaves a stray guest account, and the app gets a loaded guest profile behind the ban screen for a
  moment (here it asked `/api/friends`). Seen in 3 of 20 desktop runs. A fix would go in `ban-gate.ts` (e.g. keep a just-ended
  banned token for a short while and answer it the ban, not "no session").
- **The app asks the API behind the ban screen.** Account-driven requests (friends here) still go out while only the ban screen
  shows. Each gets the ban answer, so it's harmless, but it's traffic from a banned device.
