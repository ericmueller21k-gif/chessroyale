- **Duplicates today.**

  | Path | Status | Where |
  | --- | --- | --- |
  | Ranked coins | Exactly once (game id plus nonce). The model to copy. | ranked.ts:102-115, :132 |
  | Claw play | Exactly once (`UNIQUE (user_id, request)`). Also good. | claw.ts:13-20 |
  | Welcome grant | Exactly once (primary key on user and milestone). | welcome.ts:73-77 |
  | Solo token drop | Once (`DELETE … RETURNING`). | boss-tokens.ts:169 |

Drops have no unique key, and lobby codes are reused once a lobby closes. | lobby-do.ts:162-164, :202-203; boss-tokens.ts:46-52; codes.ts:5-9 |
  | Squads rewards | At most once. Taken out of the record before they are written, and errors are only logged, so a failed write loses the reward. | squads-do.ts:116-123, :162-164 |
  | Boss crate buy and crate opens | No request key, so a retried POST buys or opens twice. "Two taps are two buys" by design (docs/areas/shop.md). | |
- **Known and accepted.** Solo results are the device's word, and they count toward the Welcome Crate (welcome.ts:50-51,
  decision 2026-11-06-welcome-crate).

**Recommendation: an append-only ledger.** Keep the balance tables as they are; they stay the fast read and keep the CHECKs.

- **Minimal schema.**
  ```sql
  CREATE TABLE ledger (op TEXT NOT NULL, leg INTEGER NOT NULL, user_id TEXT NOT NULL,
    asset TEXT NOT NULL,     -- coins | crates | keys | token:<boss> | boss_crate:<id> | welcome:<n> | item:<def> | shop:<item>
    delta INTEGER NOT NULL CHECK (delta <> 0), reason TEXT NOT NULL, source TEXT, ref TEXT,   -- ref: the items/boss_crates row
    nonce TEXT NOT NULL, at INTEGER NOT NULL, PRIMARY KEY (op, leg));
  CREATE INDEX ledger_user ON ledger (user_id, at);
  ```
- **Write pattern.** Each grant or spend is one D1 batch built by one new module, `server/ledger.ts`.
  1. Leg 0 goes in with `WHERE <can pay> ON CONFLICT (op, leg) DO NOTHING`.
  2. The other legs, the balance updates and any `items` or `boss_crates` rows go in only
     `WHERE EXISTS (SELECT 1 FROM ledger WHERE op = ? AND leg = 0 AND nonce = ?)`.
  3. Read back leg 0's nonce. It is ours: applied. It is another attempt's: a replay, so answer the first outcome. There is none: refused.

  The nonce is what stops a retry from applying twice (ranked.ts uses the same idea). A guard on `op` alone would let a replay pass.
- **Idempotency keys** (`op`):

  | Event | Key |
  | --- | --- |
  | Online drop | `drop:<code>:<matchStart>:<user>` (the code alone is reused) |
  | Solo drop | `drop:solo:<battleId>` |
  | Squads reward | `squads:<code>:<start>:<user>` (write it before taking it out of the record, and retry) |
  | Ranked coins | `ranked:<gameId>:<color>` |
  | Coin shop | `shop:<user>:<item>` |
  | Boss crate buy, opens, claw, admin grant | `<kind>:<user>:<request>`, where the app makes one id per tap and a retry reuses it (claw.ts:43 already does) |
  | Welcome | `welcome:<user>:<n>` and `welcome-open:<user>:<n>` |
  | Item delete | `delete:<itemId>` |

- **Merge and delete.** On merge, `UPDATE ledger SET user_id` to the account in the same batch, since balances already add up.
  On account delete, rewrite the rows to the shared `deleted` id, as results are (account-data.ts:75-85). The privacy page changes
  in the same PR.
- **Backfill.** One idempotent statement per table: op `backfill:v1:<user>:<asset>`, delta = current balance minus what the
  ledger already holds for that user and asset. So it can run after the ledger writes are live and can be re-run. Each `items` row
  gets one leg at its `created_at`, with `source = items.crate`. Do not rebuild history from drops: anything older than 30 days is
  already gone.
- **Tests.**
  - Unit tests on `memory-db`: every op applied once under replay, once under a race, and not at all on a failed statement.
  - A random 500-op reconciliation over three users with merges and deletes: the sum of deltas per user and asset equals the balance, and nothing goes negative.
  - A static guard, like account-data.test's table guard: no write to a balance table outside ledger.ts.
  - Backfill run twice, and backfill after some live ops.
  - The ledger in a download/erase store, with `SCHEMA_COLUMNS` pinned.
  - `saveResults` and Squads rewards run twice, giving one drop and one reward.
  - One e2e check: a repeated request id charges once.
  - A daily reconciliation in the scheduled job, logging mismatches to `ops_errors`.
- **Effort and risk.** About 12-16 h, in two PRs, full lane. Risk: medium (stored data). The legacy balances stay the truth until the reconciliation has been clean for a week.

**Why the claw looks out of place** (close-up, phone, `SHOP_FEEL.claw` with the lens up to 3×):
- **Pixel size.** The carpet and props show about 4 CSS px (8 device px) per art pixel. The cabinet has no art pixels: its edges are 1 device px and anti-aliased.
- **Outlines.** Every room part has a 1-art-px dark outline (sprite.ts:6-8), about 4 px here. The cabinet has none; its only lines are gold posts 0.05 square wide (about 7 px).
- **Palette.** The cabinet uses 25 hex colors. 8 of them are not in Boingo's palette, including the base front (#e0447a), the crate reds and the felt (#1f6f6a). It also uses 7 translucent rgba fills.
- **Light.** Three hand-picked flat tones per box (claw-cabinet.ts:55-60). It follows neither the town's rule nor palette ramps.
- **Projection.** The cabinet is true perspective and its sides change as you move. Every other piece is a flat billboard.
- **Precedent.** Two non-pixel elements were already in rooms (the vector "you" pawn, ShopRoom.tsx:1902, and the SVG rides).
  The Colosseum's "Pixel" mode is the precedent that worked, and the owner approved it on Nov 2.

## 3. The 3D art kit

**Proposal.** The kit mostly exists already: the street town's town-kit.ts (364 lines; box, gable, hip, dome, vault and block
faces), boxes.ts (788) and box-draw.ts (276). Generalize it rather than adding an engine.

- **Primitives:** box, prism (gable), pyramid/hip, n-gon cylinder or dome, wedge, quad. Thin parts are quads 1-2 texels wide, never stroked lines.
- **Texture:** a pixel grid on every face at 37 texels a square. A flat color is a one-key grid.
- **Filtering:** nearest at 1.5× or more, smooth below, as the sprites do.
- **Palette:** the home's palette with three-step ramps. Glass is a palette alpha key.
- **Light:** flat plus 2-tone. Faces facing up or toward the light take the light ramp, fronts the base, the right side one step
  darker, and roofs are quantized from n·L. Bake the ramp swap into the face texture. Today it multiplies and lays an #0b0a12
  overlay (box-draw.ts:92-130, :256-276), which produces colors outside the palette.
- **Outline:** a 1-texel `k` ink border on each face's outer edges, as box-draw already paints. That is the sprites' 1-px weight.

**Where it lives.** `app/town/kit/`:
- `prims.ts`: pure geometry;
- `bake.ts`: faces;
- `draw.ts`: through `Painter` and camera.ts `proj`;
- `models/*.ts`: one data object each, `{ palette, textures: {name: Grid}, shapes: [{prim, at:[x,z,lift], size, faces:{front,side,top}}], anchors }`.

**Can rooms use the street town's WebGL?** Yes, through the shared `Painter` and camera. It is not `Renderer` itself, which is tied
to the world. ShopRoom calls a few things outside the `Ctx` subset (paint.ts:16-59): `createRadialGradient` ×2, `setLineDash` ×2,
`roundRect`, and a `Path2D` pawn. Those four need replacing first.

**Effort (est.).**

| Piece | Hours | Notes |
| --- | --- | --- |
| (a) The kit | 10-14 | |
| (b) The claw on the kit | 5-8 | About 150 lines of model data; claw/view.ts is kept |
| (c) One room | 12-18 | ShopRoom onto Painter (4-6) plus the room's walls and props as kit models |

**Recommendation: yes, unify buildings and props on this kit and the Painter.** No new general 3D engine and no library. The
Colosseum match keeps its own renderer, which already follows the same rules. Port a room only when it is touched.

**Risks.**
- Painter's-order sorting when a figure walks among boxes; the street town already sorts each part by its own depth.
- Software WebGL in CI is slow: the town-fixed WebGL timeouts are 400 s against 150 s for 2D (town-fixed.spec.ts:124).
- The art session's output has to become model data.
- One before/after still per room is needed when ShopRoom's draw path changes.

**Cut, in order** (est. time saved per change):
1. Stills out of the repo (a CI artifact), one shared stills script, and one still per platform: 30-60 min per visual PR.
2. Caps on docs: a decision of 10 lines or fewer, a PR body of 25 lines or fewer, area pages with their history moved out: 20-40 min per PR, plus the reading cost on every task.
3. The street town on WebGL only, and today's town's `?gl=1` retired: 10-20 min of CI and the 2D tuning on every town PR.
4. Rooms, props and intros as data (§5): hours per new home.
5. CI fixes: hooks in place of pixel diffs, a controlled clock for town-chat, full-match specs starting mid-game: a few minutes per PR, more on main.

## 6. The street town on WebGL only

**What comes out:**
- `STREET_TOWN = ADMIN_TOWN` (admin-town.ts:16) becomes `ADMIN_TOWN && hasWebGL2()`. A device without WebGL 2 gets today's town.
- Town.tsx:618 forces WebGL for the street. On a lost context it reloads into today's town instead of swapping to 2D (:559-600).
- The 2D fallback goes:
  - `LOW_ROOF` and the `low` argument (home-boxes.ts:178-219; boxes.ts:107-109, :163-175);
  - the coarse strips (boxes.ts:574-578);
  - `wallSmooth2D`, `boxStrip` and `boxStrips` (feel.ts:146, :193-194);
  - the `fine`/`kind === "webgl"` branches (render.ts:1617, :1640, :1674, :1789-1806, :1888, :1930);
  - the 2D draw-count hook (Town.tsx:1434-1435).

  That is about 120 lines of code. The bigger gain is no 12-20 draw budget and full domes.
- **Tests that stop running twice:**
  - town-fixed's 5 tests (10 runs become 5);
  - town-rows' sky check;
  - town-boxes.test.ts:176 and :192 (2D budgets) go;
  - town-street.spec moves from 2D to WebGL.

  If today's town's `?gl=1` is retired too: the two `VITE_TOWN_GL` jobs, town-webgl.spec.ts (163 lines) and town-fallback.test.ts.
